Why Git Exists

Before Git, most teams tracked changes to code by emailing zip files back and forth, or by working on one shared server and hoping nobody's edits collided. Git was built to solve that problem: it lets many people edit the same project at the same time, keeps a full history of every change, and gives everyone a complete copy of that history on their own machine.

Because every clone of a Git project holds the entire history, you can commit, branch, and inspect old versions without needing a network connection. The server only becomes relevant when you want to share your work with others.

  • Every collaborator has a full copy of the project's history
  • Changes are tracked as snapshots, not as a list of differences
  • Nothing is truly deleted until you tell Git to clean it up
Getting a Repository

A Git project lives inside a repository, which is just a regular folder with a hidden .git directory that stores the history. You end up with a repository in one of two ways: starting a brand new one, or copying an existing one from somewhere else.

To start tracking a new folder, run git init inside it. Git will quietly create the .git directory and begin watching that folder for changes, though it won't record anything until you explicitly ask it to.

To copy an existing project, run git clone followed by the repository's URL. This downloads the full history, not just the latest snapshot, which is why clones of old projects can sometimes take a while.

  • git init — start tracking the current folder
  • git clone <url> — copy an existing repository
The Basic Loop

Day-to-day Git work follows the same small loop over and over: you edit files, you stage the ones you want to record, and you commit that stage as a snapshot with a message describing what changed.

Staging exists as its own step because it lets you build a commit out of only part of what you've changed. You might have edited three files but only want to commit one of them right now — staging makes that possible.

A typical session looks like editing a file, checking what changed with git status, staging it with git add, and recording it with git commit.

  • git status — see what's changed and what's staged
  • git add <file> — stage a file for the next commit
  • git commit -m "message" — record the staged snapshot
Branching and Merging

A branch is nothing more than a movable pointer to a commit. Creating one is cheap and fast, which is why Git culture encourages branching freely for every feature, fix, or experiment rather than working directly on the main line of history.

You switch between branches with git switch (or the older git checkout), and create a new one with git branch or in one step with git switch -c.

When a branch's work is ready to combine back in, git merge brings its changes into your current branch. If both branches touched the same lines, Git will ask you to resolve the conflict by hand before the merge can finish.

Some teams prefer git rebase instead of merging, which replays your commits on top of another branch to keep history looking like a straight line rather than a web of merges.

  • git branch <name> — create a new branch
  • git switch <name> — move to a different branch
Working with Remotes

A remote is simply another copy of the repository, usually hosted somewhere like GitHub or GitLab, that you and your collaborators push work to and pull work from. Your local repository can track several remotes at once, though most projects only ever need one, conventionally named origin.

git push uploads your committed work to a remote, and git pull downloads and merges in whatever others have pushed. It's worth running git pull often, since Git will refuse a push that would overwrite history it hasn't seen yet.

For a closer look without merging, git fetch downloads a remote's history but leaves your own branches untouched until you decide what to do with it.

  • git push — send local commits to a remote
  • git pull — fetch and merge remote changes
Undoing Things

Mistakes are routine in Git, and most of them are recoverable because so little is ever truly discarded. The right command depends on how far the mistake has traveled: whether it's still sitting in your working files, staged, or already committed.

To unstage a file without losing your edits, use git restore --staged. To throw away uncommitted edits entirely and return a file to its last commit, use git restore on its own.

If the mistake is already committed, git revert creates a new commit that undoes a previous one, which is the safer option once you've shared history with others. git reset can rewrite history outright, but should be used carefully, and mainly on commits nobody else has pulled yet.

When in doubt, git log is the first place to look — it shows the trail of commits that led to where you are now, and makes it much easier to decide what to undo.

  • git restore <file> — discard uncommitted changes
  • git revert <commit> — safely undo a shared commit
